## Pipeline verified end-to-end (registered merge-attempt → TaskExecutor primitive → ProjectEngine queue → CLI processor → PG completion)

1. **`packages/core/src/merge/task-merge.ts` (new fence primitive).** `ProtectedTaskMergeFence{expectedHeadOid, admission:{runId,leaseEpoch,agentId,nodeId}, workflowId, expectedColumn}`. `ownProtectedTaskMergeFence` validates and freezes it (hex-oid regex, bounded non-empty strings ≤512 chars, `leaseEpoch` a safe positive integer) and throws `ProtectedTaskMergeRefusal("merge-authority-unavailable")` on anything malformed. `assertProtectedTaskMergeSnapshot` checks a `Task` against the fence: not deleted/paused/userPaused, `column === expectedColumn`, `workflowId` match, and all four checkout-identity fields (`checkoutRunId`, `checkoutLeaseEpoch`, `checkedOutBy`, `checkoutNodeId`) match the admission tuple — refusing `"merge-request-superseded"` otherwise. `assertProtectedTaskMergeCurrent` re-fetches `getTask`/`getTaskWorkflowSelectionAsync` fresh from the store and re-runs the snapshot check, so every call site that awaits it gets a live re-validation, not a cached one. All four checkout fields and `landedBranchTipSha`/`mergeConfirmed`/`commitSha` are pre-existing native `Task`/`mergeDetails` fields (confirmed present at base `379c94d`) — nothing invented.
2. **`packages/engine/src/executor/create-authoritative-workflow-primitives.ts` (`requestMerge` primitive — the "actual TaskExecutor primitive").** When the node config carries `requireProtectedMerge:true` (or the caller already supplied `expectedHeadOid`/`admission`), it derives the admission tuple from the task's **actual current checkout fields** (not from caller input, unless input supplies its own), fetches the **actual registered** `getTaskWorkflowSelectionAsync`/`getWorkflowDefinition`, and refuses `"merge-request-superseded"` unless `ctx.run.workflowId` equals either the registered workflow UUID or `definition.ir.name` — this is the "ctx workflow name maps against actual registered UUID selected IR" requirement, verified directly in source and confirmed live in the PG-test trace (`consumes the registered workflow UUID proof through the actual graph name context`, real `WorkflowGraphExecutor` run, `workflow:protected-merge` context correctly populated, `node:merge:value:"merged"`). The fence is built with `workflowId: selected.workflowId` (the DB-registered id), never a caller- or context-supplied value. After merge-boundary resolution it re-derives the fence with only `expectedColumn` updated to the boundary task's column — admission stays pinned to the original owner ("never borrow its replacement owner") — and re-validates via `assertProtectedTaskMergeCurrent` again before dispatch. On a protected result it interprets `merged`/`manual-required`/`merged-requested` as success and everything else as `merge-authority-unavailable`, explicitly **never** re-running the legacy finalization branch below it ("the protected native PR processor already committed its fenced completion; never run a second finalizer") — confirmed by reading the early-return before that branch. The whole body is wrapped in try/catch that converts any `ProtectedTaskMergeRefusal` into a typed failure result.
3. **`packages/engine/src/workflows/workflow-graph-executor.ts` + `workflow-merge-nodes.ts` (graph dispatch).** The legacy merge-region collapse is bypassed with `!(target?.kind === "merge-attempt" && target.config?.requireProtectedMerge === true)` — i.e. **only** an explicit protected merge-attempt node reaches its own handler; every other merge-region kind keeps the unmodified legacy collapse path. `runWorkflowMergeAttemptNode` reads the admission proof from `ctx.node.context[PROTECTED_WORKFLOW_MERGE_CONTEXT_KEY]`, refuses if absent/malformed, and refuses `"merge-request-superseded"` if `proof.taskId`/`proof.runId` don't match the executing task/run before constructing the primitive input.
4. **`packages/engine/src/project-engine.ts` (ProjectEngine queue).** `onMerge` (the human "merge now" bypass) and the automatic-sweep dispatch loop both gained a coalescing check: an incompatible concurrent request for the same `taskId` (different or missing `protectedMerge`, compared by `isDeepStrictEqual`) is refused as `"merge-request-superseded"`, while a **matching** repeat request coalesces onto the existing in-flight/queued attempt — verified live by the PG test `coalesces the identical protected request without a second provider mutation`. `workflowRequiresProtectedMerge` (reads the selected workflow's IR for a `merge-attempt` node with `requireProtectedMerge:true`) gates both `requestInterpreterMerge` and the automatic-sweep loop: an unfenced call against a protected workflow is refused before any provider work — this is the "automatic sweep cannot borrow permission" property, and it fires specifically when `!protectedMerge && !hasManualResolver`, so a manually-queued protected resolver can still be serviced by the same sweep loop without re-deriving its own fence. `assertProtectedTaskMergeCurrent` is re-checked immediately before the cross-process advisory-lock/dispatch section. Protected merges are restricted to `mergeStrategy === "pull-request"` (refusing otherwise) — direct/native-push strategies are unavailable to protected flows. Any error during a protected attempt (not just `ProtectedTaskMergeRefusal`) short-circuits the loop (`continue`, clears retry timer, rejects manual resolvers) instead of falling into the generic automatic-retry/backoff path — a protected merge is never silently retried after failure. `result === "merged" && !protectedMerge` gates the ordinary post-merge finalization block so protected flows never run it (their finalization happens exclusively in the CLI processor's atomic `moveTask` call, per point 5).
5. **`packages/cli/src/commands/task-lifecycle.ts` (CLI PR processor — "PG native completion").** `processPullRequestMergeTask` re-validates the fence (`guard()` → `assertProtectedTaskMergeCurrent`) at every await boundary: entry, after each `getPrMergeStatus` poll, after worktree-head refresh, and immediately before each `github.mergePr` call — satisfying "must survive all bridges/awaits." The wrapped `getPrMergeStatus` requires a non-empty `status.headOid` and refuses `"stale-head"` the moment it diverges from `protectedMerge.expectedHeadOid` — sourced from the real GitHub GraphQL `pr.headRefOid` field (confirmed in `dashboard/github.ts`, not synthesized). `nativeAutoMerge = settings.githubNativeAutoMerge === true && !protectedMerge` (both occurrences) and every `github.mergePr(...)` call passes `expectedHeadOid: protectedMerge.expectedHeadOid` explicitly for protected requests, never `auto:true` — satisfying "no native auto=true," exactly as documented in `task-merge.ts`'s own comment. `finalizePullRequestMerge` calls `assertProtectedTaskMergeCurrent` once more, then calls `store.moveTask(task.id, completeColumn, {protectedMerge})` as the **sole** completion write, with cleanup (`cleanupMergedTaskArtifacts`) deferred to *after* that call for protected requests — matching "old status/prInfo updates remain nontransactional, final native completion fenced." Protected merges are explicitly excluded from branch-group and workspace tasks (`!task.prInfo || task.branchContext?.groupId || isWorkspaceTask(task)` refuses) — matches "current 303 required node top-level; no generalized nested policy claim."
6. **`packages/core/src/task-store/moves.ts` (final atomic completion).** A cheap preliminary check runs against the already-loaded `readTaskForMove` snapshot (avoiding the recursive-lock hazard the HANDOFF's negative-evidence section describes: calling public `getTask` from inside `moveTask` would re-enter task locking). The **authoritative** check happens inside the existing DB transaction: `SELECT ... FOR UPDATE` row-locks the task, re-reads it fresh, and re-runs `assertProtectedTaskMergeSnapshot` against that locked row — closing the TOCTOU gap the scope file calls out. It then additionally requires `toColumn === (moveLifecycle?.complete ?? "done")` (workflow-resolved terminal column, not a hardcoded literal), `current.prInfo.status === "merged"`, and **`current.prInfo.headOid === options.protectedMerge.expectedHeadOid`** (the provider-confirmed head must equal the originally reviewed/captured head) before writing `mergeDetails = {...current.mergeDetails, mergeConfirmed:true, landedBranchTipSha: options.protectedMerge.expectedHeadOid, mergedAt: new Date().toISOString()}` and clearing `status`/`mergeRetries`/`mergeTransientRetryCount`, all inside the same transaction that then calls `upsertTaskRowInTransaction`. `commitSha` is never touched by this block — confirmed by grep across the full diff, matching the HANDOFF's explicit claim that `landedBranchTipSha` records the reviewed source/task branch tip, not an attested destination merge commit, and that `commitSha` stays unset unless the provider separately attested it.
